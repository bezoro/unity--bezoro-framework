# Working on the shared Unity utilities

This repository contains the current Unity utility source as the `com.bezoro.unity-framework` UPM package. Its `DevProject~` development project imports the local package and resolves the pure C# Framework through Package Manager. Chess Crush retains its separate legacy installation at `Assets/_Bezoro/Unity`; adding the development project does not migrate or modify that game. The source and test trees retain their Unity `.meta` files and assembly names. The repository history also retains the older framework implementation; the migration replaces its active asset tree with the evolved Chess Crush source.

Use the nested checkout in Chess Crush as the current editable source. Open that exact directory in another editor or workspace if desired. Edits appear both in Chess Crush and in this repository's Git status immediately, because both use the same directory. Independent clones share committed changes through normal Git operations.

Commit and publish utility changes here before publishing a game revision that records the new submodule commit. A framework commit or push does not update the game automatically. The game stores a pinned commit and must explicitly record a tested replacement. The game helper `Tools/UnityFramework.ps1` provides status, tracked diffs, fetch-only operation, and clean-checkout revision staging. It never commits or pushes.

After `git submodule update`, check the current branch before editing. The checkout may have a detached HEAD. Create or switch to an intended branch, preserve dirty work, and avoid forced updates.

Keep Unity and pure C# roles separate. `bezoro/framework` publishes `com.bezoro.framework` on its `upm` branch. `DevProject~/Packages/manifest.json` pins an immutable published Git revision and enables this local package's tests. Keep the package manager's generated lock after a real resolution; do not copy the package's DLLs into Assets or edit PackageCache. Git dependencies must be declared by the consuming project because UPM does not support Git dependencies between packages. Existing DLL-name references in assembly definitions select the UPM-provided assemblies. Third-party content and editor feedback audio remain outside this repository. The audio normalizer still defaults to the legacy consuming project's `VO` folder; another project should choose its own audio folder in the tool.

Use the development project's exact Editor for local work. Full native compilation remains dependent on the real KCC and ALINE integrations and the existing consumer-specific test helpers listed in `README.md`. The UPM manifest does not replace those integrations. Do not modify a consuming game to complete work in this repository unless the user asks for it. Preserve `.meta` files, GUIDs, assembly references, and serialized asset references when changing utilities. `DevProject~` and `~Docs` are ignored by package asset import.

The root `.gitattributes` retains the consuming game's existing line-ending and Git LFS policy. Install Git LFS before cloning or publishing assets covered by its filters, and fetch LFS objects when needed. Keep this policy with the framework so its Git blobs use the same normalization as the game source. Before an authorized framework branch push, run `git lfs push origin <framework-branch>` if a Git LFS pre-push hook is unavailable; upload the LFS objects before publishing the game pointer.
